PostgreSQL 반복 재시작 원인 분석 및 복구

  1. 01재현으로 범위 좁힘
  2. 02손상 행 추적ctid · TOAST
  3. 03하드웨어 이벤트 로그·부팅 기록 대조
  4. 04강제 전원 차단 확정
  5. 05재적재 안내
  6. 06복제본 재구성3 → 2 → 3
  7. 07타임아웃 60초
증상
Kubernetes 오퍼레이터(CloudNativePG)로 운영하던 PostgreSQL이 약 800만 행 테이블을 조회할 때마다 재시작됐고, 다음 날에는 복제본이 200회 넘게 재시작하며 주 서버(primary)가 계속 바뀌었습니다.
원인
로그의 손상 행을 물리 위치(ctid)로 따라가 큰 값을 따로 저장하는 영역(TOAST)의 첫 조각이 빠진 것을 찾았습니다. 하드웨어 이벤트 로그(IPMI SEL)의 강제 전원 차단 기록(S5: entered by override)과 journalctl 부팅 이력을 대조해 디스크·OS 문제가 아니라 예기치 않은 전원 차단임을 확정했습니다. 쓰기 도중 전원이 끊겨 TOAST 데이터가 손상된 것으로 판단했고, 반복된 재시작과 주 서버 전환으로 복제본의 WAL 타임라인이 어긋났습니다.
해결
손상된 테이블은 재적재로 복구하도록 안내했고, 복제본은 Pod·PVC·PV를 지운 뒤 클러스터를 3 → 2 → 3으로 조정해 복제를 다시 구성했습니다.
재발 방지
복제본 재시작이 반복되지 않도록, 5초로 짧게 잡혀 있던 wal_sender_timeout · wal_receiver_timeout을 CloudNativePG GitHub 이슈를 근거로 PostgreSQL 기본값인 60초로 변경했습니다.
