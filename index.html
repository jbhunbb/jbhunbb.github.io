일하는 방식

같은 일을 두 번 하게 되면 도구로 만듭니다. 다만 만든 사람만 이해하는 자동화는 고장 날 때마다 그 사람이 손으로 챙겨야 하므로, 다음 사람이 읽고 고칠 수 있는 구조를 더 중요하게 봅니다.

01

반복되면 도구로

메신저로 받아 손으로 처리하던 배포 요청은 Teams 챗봇과 ArgoCD로, 클라우드 다섯 곳의 콘솔에서 하나씩 만들던 고객 환경은 Terraform과 Jenkins 파이프라인으로 바꿨습니다.

02

바꾸기 전에 복구할 길부터

EKS는 한 번 올린 버전을 되돌릴 수 없습니다. 그래서 사라지는 API와 애드온 호환성을 먼저 확인하고, Velero로 백업하고, 스테이징에서 리허설한 뒤에 한 버전씩 올렸습니다.

03

증상보다 원인

PostgreSQL이 계속 재시작될 때 재시작만 멈추고 끝내지 않았습니다. 손상된 행과 서버 하드웨어 로그까지 따라가, 원인이 강제 전원 차단이었음을 확인했습니다.

04

검증은 기준부터

이미지 개수만 세던 검증이 시스템 이미지가 빠진 빌드를 통과시킨 뒤로, 이미지마다 태그와 레이어까지 확인하게 바꿨습니다. 잘못된 설정값은 서버를 바꾸기 전에 거부하는지 341가지 경우로 시험했습니다.

고객사 PoC 환경에서 Kubernetes 오퍼레이터(CloudNativePG)로 운영하던 PostgreSQL이 약 800만 행 테이블을 조회할 때마다 재시작됐습니다. 다음 날에는 복제본이 200회 넘게 재시작하면서 주 서버(primary)가 계속 바뀌었습니다.
원인
로그에 찍힌 손상 행을 물리 위치(ctid)로 따라가 보니, 큰 값을 따로 저장하는 영역(TOAST)의 첫 조각이 빠져 있었습니다. 서버 하드웨어 로그(IPMI SEL)의 강제 전원 차단 기록과 부팅 이력(journalctl)을 대조해, 원인이 예기치 않은 전원 차단임을 확정했습니다. 데이터를 쓰는 도중 전원이 끊겨 손상됐고, 재시작과 주 서버 전환이 반복되면서 복제본의 복제 이력(WAL 타임라인)도 어긋났습니다.
해결
손상된 테이블은 원본 데이터를 다시 적재해 복구하도록 안내했습니다. 복제본은 인스턴스 수를 3 → 2 → 3으로 조정해 복제를 처음부터 다시 구성했습니다.
추가 조치
재시작의 직접 원인은 아니었지만, 5초로 짧게 잡혀 있던 복제 송수신 타임아웃(wal_sender_timeout · wal_receiver_timeout)을 CloudNativePG GitHub 이슈를 근거로 PostgreSQL 기본값인 60초로 되돌렸습니다.
